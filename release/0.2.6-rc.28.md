# Vista Turbo RS232 0.2.6 RC28

RC28 hardens the Home Assistant-facing MQTT transport after a field incident where Home Assistant reported the VISTA entities offline and unavailable while the bridge continued communicating normally with the panel. Restarting the App restored the entities.

The captured field log proves that the VISTA TCP/session side remained healthy through the incident, but it does not include the beginning of the MQTT failure. RC28 therefore addresses the observed failure mode rather than claiming an unproven single Paho root cause.

## MQTT liveness watchdog

- Add a non-retained QoS 1 heartbeat every 15 seconds while MQTT is connected.
- Require broker PUBACK progress rather than treating a successful local `publish()` call as proof that the Paho network loop is healthy.
- If a heartbeat remains unacknowledged for 60 seconds, replace the Paho client and network loop without restarting the VISTA connection or the App.
- If MQTT remains disconnected without connection progress for 60 seconds, replace the transport client as a second recovery path.
- Ignore callbacks from a superseded client after watchdog replacement.
- Suppress Paho callback exceptions so one callback exception cannot terminate the network loop without the watchdog detecting the resulting loss of progress.

## Home Assistant recovery

- Treat every successful MQTT connection, including the initial connection and watchdog recovery, as a request for a complete Home Assistant-facing replay.
- Republish MQTT Discovery outside the Paho callback thread.
- Republish panel connectivity, state freshness, automation availability, metrics, partition state, keypad state, assigned-zone state, zone summaries, alarm state, event-journal state, and the last event when authoritative data is available.
- Keep `bridge/availability` offline until discovery and the authoritative replay complete.
- If any replay publication is rejected, leave Home Assistant unavailable and retry the replay instead of exposing a partial entity set.
- Keep the VISTA panel session authoritative. MQTT recovery does not force a panel reconnect or invalidate otherwise-current VISTA state.

## Startup behavior

- Do not enqueue normal state publications before Paho has completed the broker connection.
- Remove the harmless startup `MQTT_ERR_NO_CONN` / `rc=4` burst that could occur just before the broker connected.
- Preserve the finite 4096-message production outbound queue introduced in RC15.

## Diagnostics

- Add the disabled-by-default `MQTT Watchdog Restarts` diagnostic sensor.
- Continue counting ordinary MQTT publication errors separately.

## Architecture

ADR 0001 remains the long-term direction. The App stays the sole VISTA protocol/domain engine, the future native `custom_components/vistaturbo` integration will consume a private authenticated push API/WebSocket, and MQTT will become optional compatibility output once native parity is sufficient. RC28 does not expand MQTT into a new architectural dependency.

## Test maintenance

- Make three event-retention tests independent of the wall-clock date. Their August 2026 fixtures had crossed the 30-day automatic-pruning boundary by September 23, 2026; production retention behavior is unchanged.
